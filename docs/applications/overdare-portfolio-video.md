# 포트폴리오 영상 — 시나리오 · 편집 · 자동화

| 항목 | 값 |
| --- | --- |
| 대상 | `/portfolio/overdare/` 16장 덱에 들어갈 영상 |
| 전제 | 각 프로젝트의 원본 영상과 지표 스크린샷은 준비돼 있다 |
| 도구 | ffmpeg (미설치 — 5절) + `tools/video/render.js` + Claude Code |
| 장 구성 | `overdare-tpm.md` 4.4절 |

---

## 1. 원칙 다섯 가지

1. **영상은 문서를 보조한다.** 영상이 주가 되면 쇼릴이고, 쇼릴은 TPM 포트폴리오가 아니다.
   각 영상은 그 장이 증명하려는 것 하나를 위해 존재한다.
2. **검토자는 5분을 보지 않는다.** 게임플레이는 30–60초. 전체 합계 8분 이내.
   예외는 파이프라인 워크스루(2–3분) 하나.
3. **무음으로 봐도 이해돼야 한다.** 채용 담당자는 사무실에서 소리를 끄고 본다.
   설명이 필요한 것은 전부 자막. 음악은 넣어도 되지만 없어도 성립해야 한다.
4. **가장 중요한 영상은 게임플레이가 아니다.** 파이프라인 워크스루 — Claude Code 세션 →
   산출물 → 인게임. "보여 줄 수 있나" 의 답이자 면접 시연의 예고편.
5. **검증 프로토타입은 툴 화면과 검증 결과가 먼저다.** UEFN·Horizon 두 건은 플랫폼 테스트용이라
   게임보다 에디터와 "무엇을 알아냈나" 가 요점이다. 플레이만 보이면 "그래서 언리얼을 썼다는
   증거가 어디 있나" 가 된다.

## 3. 시나리오

시간은 목표치다. 컷은 2–4초, 첫 컷은 1초 안에 무엇인지 알 수 있어야 한다.

### 3.1 `tfr-pipeline.mp4` — 파이프라인 워크스루 (가장 중요)

**증명**: "AI 가 만들었다면 당신은 무엇을 했나" 에 대한 시각적 답. 검토 메모 2절 Q2.

| 막 | 시간 | 화면 | 자막 |
| --- | --- | --- | --- |
| 도입 | 0:00–0:10 | 타이틀 카드 → 지표 대시보드(11.05M) | "3인 스튜디오 · 라이브 6종 · 어떻게" |
| 1. 계기 | 0:10–0:30 | 지표에서 문제 발견(리텐션 하락, 특정 구간 이탈 등) 또는 업데이트 기획 메모 | "무엇을 만들지는 사람이 정한다" + 결정 내용 한 줄 |
| 2. 위임 | 0:30–1:30 | Claude Code 세션. 프롬프트 입력 → 에이전트 작업(4–8배속) → 산출물. **지침 문서(rule.md)가 화면에 한 번 보이게** | "에이전트가 하는 것: X" / "지침 문서가 정하는 것: 규약·금지·검토 조건" |
| 3. 검토 | 1:30–2:00 | 사람이 산출물을 읽고 고치는 장면. **되돌리는 순간 하나** | "사람이 하는 것: Y" / "이 부분은 되돌렸다 — 이유" |
| 4. 결과 | 2:00–2:30 | Studio 배포 → 인게임에서 그 기능 동작 | "배포까지 N시간" |
| 마무리 | 2:30–2:45 | 엔드 카드 | 경과 시간 · 반복 주기(주 N회) |

- **3막이 핵심이다.** 사람이 개입하는 장면이 없으면 "AI 가 했고 나는 봤다" 로 읽힌다.
  되돌리는 순간을 반드시 넣는다.
- 에이전트 작업 구간은 배속하되 프롬프트와 최종 산출물은 정속으로 읽을 수 있게.
- 화면 녹화: Windows `Win+G`(Game Bar) 또는 OBS. 1080p, 터미널 글꼴 크기를 키운다.
- 이 영상은 면접 시연과 같은 흐름이어야 한다. 면접에서는 이것을 라이브로 한다.

## 4. 편집 방향 — 공통 규격

| 항목 | 규격 |
| --- | --- |
| 해상도 · fps | 1920×1080 · 30fps. 세로 원본(모바일)은 좌우 패딩 |
| 코덱 | H.264 (libx264, CRF 20) · MP4 · faststart |
| 타이틀 카드 | 2.5초. 어두운 배경(`#14171b`) · 흰 제목 · 회색 부제. 부제 = 플랫폼 · 시기 · 지표 한 줄 |
| 엔드 카드 | 2초. 사이트 주소 |
| 자막 | 하단 1/5 지점, 흰 글자 + 반투명 검정 띠. 한 줄 20자 이내. 한 번에 한 줄 |
| 컷 리듬 | 게임플레이 2–4초/컷. 툴 화면 4–6초/컷(읽어야 한다). 워크스루 정속·배속 구분 |
| 음악 | 없어도 성립. 넣으면 가사 없는 것, -18 LUFS. 워크스루는 무음 권장 |
| 글꼴 | Windows: 맑은 고딕(`malgun.ttf`) — 한글 자막 |
| 파일명 | 2절 표 그대로. 소문자·하이픈 |
| 위치 | `portfolio/overdare/assets/` |

**같은 규격이 열 개 영상에 반복되면 그것 자체가 "체계적으로 일하는 사람" 의 신호다.**
타이틀 카드 스타일이 영상마다 다르면 반대 신호다.

## 5. Claude Code 자동 편집

원본 정리와 컷 선택은 사람이 하고, 규격 맞추기·카드 생성·자막·인코딩은 에이전트가 한다.
이 분담 자체가 3.1 영상이 보여 주는 것과 같다 — 포트폴리오 제작 과정이 곧 포트폴리오다.

### 5.1 준비

```
winget install Gyan.FFmpeg        # ffmpeg + ffprobe. 설치 후 새 터미널
```

원본을 `raw/<프로젝트>/` 에 모은다. 파일명은 자유 — spec 에서 가리킨다.

### 5.2 흐름

```
raw/               원본 (사람이 모은다)
tools/video/
  spec.json        영상마다 하나의 항목 — 어떤 원본의 몇 초부터 몇 초까지, 어떤 자막, 어떤 카드
  render.js        spec → ffmpeg. --dry-run 이면 명령만 출력
portfolio/overdare/assets/   결과물
```

1. **컷 선택은 사람이.** 원본을 보고 쓸 구간(`in`/`out`)과 자막을 고른다. 이 판단은 위임하지
   않는다 — 어떤 3초가 게임을 대표하는지는 만든 사람만 안다.
2. **spec 작성은 에이전트에게.** 3절 시나리오와 고른 구간을 주고 `spec.json` 항목을 쓰게 한다.
   "3.5 시나리오대로 get-train 항목을 만들어. 구간은 이것" 이면 된다.
3. **`--dry-run` 으로 명령 확인.** 에이전트가 만든 spec 이 의도와 맞는지 명령을 읽어 본다.
4. **렌더.** `node tools/video/render.js` — spec 의 모든 영상을 규격대로 만든다.
5. **검토 → 수정 루프.** "tfr-gameplay 두 번째 컷 1초 짧게, 자막 크게" 처럼 말하면 에이전트가
   spec 을 고치고 다시 렌더한다. 편집 프로그램을 열지 않는다.

### 5.3 에이전트가 맡는 것 / 사람이 보는 것

| 에이전트 | 사람 |
| --- | --- |
| 해상도·fps·코덱 통일 | 어떤 구간을 쓸지 |
| 타이틀·엔드 카드 생성(텍스트 → 카드) | 자막 문구 |
| 자막 번인, 위치·크기 일관성 | 컷 순서와 리듬이 맞는지 |
| 세로 원본 패딩, 오디오 정규화 | 프로토타입·시기 표기가 정직한지 |
| spec 수정 → 재렌더 | 최종 승인 |

### 5.4 spec 형식

`tools/video/spec.example.json` 참고. 항목 하나:

## 6. 덱에 넣기

```html
<!-- 게임플레이: 슬라이드가 열리면 무음 반복. 첫 프레임을 poster 로 -->
<video src="assets/tfr-gameplay.mp4" poster="assets/tfr-gameplay.jpg"
       muted autoplay loop playsinline></video>

<!-- 워크스루: 사용자가 재생. 자막이 있으므로 controls -->
<video src="assets/tfr-pipeline.mp4" poster="assets/tfr-pipeline.jpg"
       controls playsinline preload="metadata"></video>
```

- PDF 로 뽑을 때는 영상이 poster 이미지로 찍힌다. poster 를 반드시 둔다 — 첫 프레임을
  `ffmpeg -ss 1 -i x.mp4 -frames:v 1 x.jpg` 로.
- `deck.js` 의 PDF 버튼은 `<img>` 만 강제 로드한다. `<video poster>` 는 브라우저가 처리한다.
- 슬라이드 하나에 영상 하나. 둘 이상이면 어느 것을 봐야 할지 모른다.

**저장소 용량** — 1080p CRF 20 으로 30–60초면 5–15MB, 열 개면 100MB 안팎이다. GitHub 은
파일당 100MB 제한이 있고 저장소가 무거워진다. 원본(`raw/`)은 `.gitignore` 에 넣었다.
결과물은 커밋해도 되지만 전체가 50MB 를 넘기면 YouTube(비공개 링크) 에 올리고 덱에는
`<iframe>` 대신 poster 이미지 + 링크로 두는 편이 낫다 — PDF 에서도 깨지지 않는다.
